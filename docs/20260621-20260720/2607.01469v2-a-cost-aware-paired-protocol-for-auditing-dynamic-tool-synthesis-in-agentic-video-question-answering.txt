## Abstract 

Agentic Video Question Answering (VideoQA) systems in-voke tools during inference, but their tool libraries are fixed, so recurring procedures are rebuilt from primitives on every question. Synthesizing composite tools could re-move this overhead, but whether such expansion helps is hard to assess: final-answer accuracy, the standard met-ric, ignores inference effort, so it cannot reveal how a sys-tem shifts cost. We propose a cost-aware, paired proto-col for auditing tool-augmented video agents. The proto-col pairs two complete systems on the same input for each question and reports their net difference across accuracy and cost jointly. For each question, it sorts the paired outcome into one of six groups defined by joint correct-ness and by the change in visible tool calls, separating accuracy-preserving efficiency gains from harmful regres-sions. Significance is reported with McNemar’s test and paired bootstrap confidence intervals. We instantiate the protocol on Dynamic-SAGE, an agentic VideoQA frame-work that synthesizes, validates, and persistently registers executable composite tools for reuse on unseen questions, and evaluate it against the SAGE baseline on SAGE-Bench. The audit reveals a multi-axis profile that a scalar accuracy comparison would miss: Dynamic-SAGE improves accu-racy by 7.5 points ( p < 0.001 ) and reduces reasoning turns and visible tool calls by roughly 28%, while shifting rather than reducing inference cost, as token usage rises 34% and cost 26%. Gains are largest on visual and open-ended questions and neutral on verbal and multimodal ones, and residual failures concentrate on hard, open-ended ques-tions where the pipeline does the most work. ## 1. Introduction 

Video Question Answering (VideoQA) tests whether a model can locate and reason over the question-relevant ev-idence in a video [8, 19, 20]. A core challenge is that the evidence needed to answer a question is often sparse and question-dependent [9, 19]. A short clip, a spoken phrase, a visible object, or a brief event may determine the correct answer, while most of the video may be irrelevant. Pro-cessing videos uniformly is therefore inefficient, especially for long-form content, yet aggressive sampling can miss the evidence required for accurate reasoning [19]. An effective 1

> arXiv:2607.01469v2 [cs.CV] 3 Jul 2026

VideoQA system must decide which parts of the video are relevant, which modality to inspect, and which reasoning operations are needed to answer the question. Early VideoQA systems committed to these decisions up front, encoding sampled frames with a vision-language model and answering in a single pass [10, 11, 21]. This leverages the broad visual and linguistic knowledge of mod-ern multimodal models, but places the entire burden on one static video representation. When the relevant evidence is brief or appears far from the sampled frames, uniform or heuristic sampling can omit information needed to an-swer [10, 19]. To recover selectivity, recent modular VideoQA methods decompose answering into intermediate stages [2, 14]. A composite tool could instead expose that recurring sequence as a single reusable action, amortizing repeated planning and tool-selection overhead while preserving the same un-derlying primitive capabilities. More recent agentic VideoQA systems push this further, letting an LLM or multimodal controller iteratively invoke tools during inference [4, 7, 15]. SAGE, for example, in-troduces an any-horizon video reasoning agent that answers simple questions directly and escalates to multi-turn reason-ing for more complex long-video questions [7]. The set of available tools is still specified before inference and remains fixed during evaluation. This distinction is central to our work: existing agentic VideoQA systems are dynamic in 

how they use tools, but static in what tools are available. Motivated by this gap, we propose Dynamic-SAGE , a framework that equips an agentic VideoQA system with a dynamically expandable tool library. Starting from a held-out set of VideoQA questions and an existing primi-tive tool set, an offline pipeline identifies recurring tool-use trajectories and compiles them into executable composite tools: a signature agent proposes candidate tool interfaces, an implementation agent composes existing primitive op-erations into executable functions, and a verification agent removes duplicate, malformed, or unsafe candidates before the rest are registered. Dynamic-SAGE thus extends agen-tic VideoQA from dynamically selecting among predefined tools to dynamically expanding the reusable action space itself. Figure 1 illustrates the key difference between Static-SAGE and Dynamic-SAGE, highlighting how synthesized composite tools restructure inference cost. Final-answer accuracy, the standard VideoQA metric, re-ports only whether the system is correct, not how much in-ference effort the answer cost. It therefore cannot reveal whether enlarging the action space saves effort, shifts it, or trades accuracy for efficiency. To study this question rather than assume it, we pair Dynamic-SAGE against its static baseline on the same questions and audit the two systems jointly across accuracy and cost. The audit shows that the change is not a single number: Dynamic-SAGE improves accuracy and reduces reasoning turns and visible tool calls, yet shifts cost toward per-call token consumption rather than reducing every axis. This is the multi-axis profile a scalar accuracy comparison would miss, and motivating the protocol is as central to our contribution as the system it evaluates. The main contributions of this paper are summarized as follows: • A cost-aware, paired evaluation protocol. Our primary contribution is a protocol for auditing tool-augmented video agents that pairs two complete systems on every question and reports their net difference across accuracy and cost jointly, rather than collapsing performance to a single accuracy number. It sorts each paired outcome into one of six groups defined jointly by correctness and by the change in visible tool calls, and reports significance with McNemar’s test and bootstrap confidence intervals. This separates accuracy-preserving efficiency gains from harmful regressions and provides a reusable practice for studying tool synthesis rather than a single comparison. • Dynamic-SAGE, a testbed for tool synthesis. We build an agentic VideoQA framework that synthesizes, val-idates, and persistently registers executable composite tools for reuse on unseen questions. An offline pipeline of signature, implementation, and verification agents pro-poses candidate tool interfaces, composes them from ex-isting primitives, and rejects invalid, duplicate, unsafe, or non-compositional candidates before registration. The system adds no new models, retrieval sources, or primi-tive capabilities. • A multi-axis audit of a synthesized-tool pipeline on SAGE-Bench. Applying the protocol to Dynamic-SAGE against the SAGE baseline, we find that the redesigned pipeline improves overall accuracy by 7.5 points ( p < 

0.001 ) and reduces reasoning turns and visible tool calls by roughly 28%, while increasing token usage by 34% and monetary cost by 26%, a multi-axis profile that a scalar accuracy comparison would miss. We localize the effect with the protocol: gains are largest and significant on visual and open-ended questions, while verbal and multimodal questions are neutral, and the residual fail-ures concentrate on hard, open-ended questions where the pipeline does the most work. 

## 2. Related Works 

2.1. Video Question Answering 

Video Question Answering (VideoQA) has evolved from answering questions about short clips toward evaluating temporal reasoning, causal action understanding, long-context comprehension, and multimodal evidence ground-ing [8, 12, 19, 20]. Early benchmarks such as TVQA and NExT-QA require models to reason over video events, di-2alogue, object interactions, and temporal relations [8, 20]. Recent benchmarks such as EgoSchema, LongVideoBench, SAGE-Bench, and MINERVA challenge long-form under-standing, multi-step reasoning, and failure analysis [7, 12, 16, 19]. 

2.2. End-to-end MLLMs 

Multimodal large language models extend image-language modeling to video by processing sampled frames or com-pressed visual representations together with text, leverag-ing pretrained visual encoders and large language mod-els [10, 11, 21]. However, extending these models to long videos introduces a difficult efficiency trade-off. Processing more frames increases visual-token and computation costs, while sparse or uniform sampling can omit short answer-bearing moments [10, 19]. 

2.3. Agentic Systems 

To address sparse and question-dependent evidence, recent work has explored modular and agentic VideoQA systems. Modular methods such as MoReVQA and ProViQ decom-pose answering or generate programs over a predefined API of visual modules [2, 14], making intermediate reasoning more explicit but specifying their modules before inference. Agentic systems extend this idea by allowing an LLM or multimodal controller to iteratively invoke tools during in-ference [4, 7, 15]. However, existing VideoQA agents re-main dynamic only in tool selection and sequencing; the tool library itself is fixed. A related line of work lets models create their own callable procedures rather than only selecting from a fixed set. Visual-programming methods such as VisProg and ViperGPT compose vision modules into executable pro-grams per question, generating Python that calls a prede-fined module API [5, 17]. These approaches generate pro-cedures per query : the composed program is discarded af-ter the question is answered and must be regenerated for the next one. VADAR moves toward reusable creation, us-ing collaborative LLM agents to generate a Pythonic API for image-based 3D spatial reasoning [13], but targets static images rather than video. Dynamic-SAGE differs from this literature in three ways. First, its synthesized tools are persistent : they are built once, offline, and registered in the agent’s action space for reuse across unseen questions, rather than regen-erated per query. Second, they are composed only from a video agent’s own primitives, so they add no new exter-nal capability. Third, they are checked offline before use and evaluated under a cost-aware protocol. VideoQA also introduces temporal and multimodal requirements absent from image-based program synthesis, including event lo-calization, frame extraction, speech transcription, and long-context evidence selection. Dynamic-SAGE addresses this gap by extending SAGE with a dynamic synthesis layer that generates, validates, and persistently registers compos-ite tools for reuse on unseen VideoQA questions. 

## 3. Methods 

Dynamic-SAGE is a dynamic tool-synthesis extension of SAGE that combines the original agentic VideoQA infer-ence pipeline with an offline multi-agent tool-generation module. Unlike prior VideoQA agents that dynamically select among fixed tools, Dynamic-SAGE dynamically ex-pands the reusable action space itself while preserving the same underlying primitive capabilities. 

3.1. Overview 

We formulate the task in three layers: standard VideoQA, agentic VideoQA, and dynamic tool synthesis. Let a VideoQA dataset be denoted as 

D = {(Vi, q i, a i)}Ni=1 , (1) where Vi is a video, qi is a natural-language question, and ai

is the ground-truth answer. Some questions include a can-didate answer set Ci = {ci, 1, . . . , c i,K i }, while open-ended questions use Ci = ∅. The standard VideoQA objective is to produce a prediction ˆai = M (Vi, q i, Ci) that matches ai.In agentic VideoQA, the answer is produced through a sequence of reasoning turns and tool calls rather than a sin-gle forward pass: given a tool library T and a reasoning orchestrator O, the agent predicts ˆai = O(Vi, q i, Ci; T ),where O may execute a multi-step tool-use trajectory be-fore producing the final answer. Each tool call receives ar-guments constructed from the question, video context, and previous observations, and returns an intermediate observa-tion used to guide subsequent reasoning. The dynamic tool-synthesis problem is to construct an expanded tool library before evaluation. Let Ts denote the original Static-SAGE ( GPT-4o orchestrator) tool library and let Dh ⊂ D be a held-out synthesis set excluded from evaluation. Dynamic-SAGE learns no new model weights; instead, it applies a synthesis procedure S to generate a set of composite tools: 

Td = S(Dh, Ts). (2) We compare the static and dynamic systems as complete pipelines that share a single, multimodal orchestrator. Each pipeline produces a prediction on the same input: 

ˆasi = O(Vi, q i, Ci; Ts),

ˆadi = O(Vi, q i, Ci; Ts ∪ T d). (3) The two systems differ only in their action space ( Ts versus

Dynamic-SAGE comprises three stages: (1) offline dynamic tool synthesis, (2) Context VLM, and (3) Iterative Reasoner. The offline synthesis stage takes held-out queries Dh (excluded from evaluation) and the static tool set Ts as input. The Signature Agent proposes tool signatures, which the Implementation Agent turns into function bodies by composing static tools. The Verification Agent then validates each implementation for safety and contract compliance, returning failures to the Implementation Agent for retry; surviving tools are fingerprinted and deduplicated to form the dynamic tool library Td. 3.2. Dynamic-SAGE 

Dynamic-SAGE consists of two stages: (1) offline tool syn-thesis and (2) inference-time reasoning. Before evaluation, given the held-out synthesis set Dh and the Static-SAGE tool library Ts, a multi-agent synthesis module proposes, implements, and verifies candidate composite tools, produc-ing the dynamic library Td.During inference, the SAGE orchestrator receives the ex-panded library Ts ∪ T d. For each unseen evaluation ques-tion, it follows the same multi-turn reasoning process as the static baseline, but may now invoke either primitive tools or synthesized composite tools. A composite tool appears to the orchestrator as a single action, while internally exe-cuting a fixed composition of primitive operations. Thus, Dynamic-SAGE does not introduce new external models, retrieval sources, or primitive capabilities. Recurring multi-step procedures can be exposed as reusable high-level ac-tions instead of being reconstructed from primitive tools at every inference run. 

3.3. Static and Dynamic Tool Libraries 

Let the Static-SAGE tool library be denoted by Ts, as sum-marized in Table 1. This library contains the primitive tools available to the original SAGE agent, including web search, website parsing, speech transcription, event ground-ing, video-part extraction, and multimodal analysis. Static-SAGE performs adaptive inference by selecting and se-quencing tools from Ts, but the tool inventory itself remains fixed. Dynamic-SAGE augments Ts with a synthesized library 

Td = {g1, g 2, . . . , g K }, (4) where each gk is a persistent composite tool constructed only from primitives in Ts.Dynamic-SAGE uses a three-agent synthesis procedure, consisting of signature, implementation, and verification agents, inspired by VADAR [13]. In contrast to VADAR’s dynamic API for 3D spatial reasoning, Dynamic-SAGE 4synthesizes composite tools over the SAGE VideoQA tool library and registers them in the agent’s reusable action space for unseen questions. A composite tool has the same external form as a primi-tive tool, which includes a name, natural-language descrip-tion, argument schema, return schema, and executable body. The difference is that its body invokes an ordered sequence of existing primitive tools. We represent this internal com-position as 

ρ(gk) = ( tk, 1, t k, 2, . . . , t k,d k ), tk,j ∈ T s, (5) where dk is the depth of gk, defined as the num-ber of primitive operations it encapsulates. For ex-ample, a depth-2 composite tool can express a re-curring speech-based pattern such as ground event 

→ transcribe speech , while a deeper compos-ite tool can express a visual-temporal pattern such as ground event → extract video parts →

analyze .The terminal operation of a composite tool is constrained by an evidence-return contract: when a composition ends in analyze , that step is invoked in observe mode, so it returns intermediate observations rather than a committed answer. Some composites omit a terminal analyze step entirely and return raw evidence directly. In both cases, an-swer commitment is reserved for the orchestrator, and no synthesized tool emits a final verdict to avoid false confi-dent answer verdicts. Finally, synthesized tools are persistent . Once accepted by the verification stage, they are added to the tool registry before evaluation and remain available for all unseen ques-tions. This distinguishes Dynamic-SAGE from per-query program generation. Dynamic-SAGE does not create a tem-porary program for each input; it expands the reusable tool library itself. 

3.4. Offline Dynamic Tool Synthesis 

Dynamic-SAGE constructs Td before evaluation using an offline synthesis pipeline. The synthesis stage takes as input the Static-SAGE tool descriptions and a held-out set Dh of 150 stratified questions, excluded from final evaluation and processed in batches of 15. Algorithm 1 in Appendix S1 summarizes the offline syn-thesis procedure, completed before evaluation. The orches-trator never writes Python at inference time, and the eval-uation runtime differs from Static-SAGE only by the addi-tional registered tools in Td.The pipeline runs three agents. Signature Agent. Given a batch of held-out questions and descriptions of the Static-SAGE tools, it identifies recurring multi-step reasoning pat-terns and proposes between two and five candidate tool in-terfaces, each specifying a name, a short description, the required inputs, the expected output, and the intended se-quence of primitive operations. Implementation Agent. 

For each signature it generates the tool body, a thin Python function calling existing SAGE tools, constrained to use the existing signatures exactly: it cannot add external depen-dencies, call new models, or perform new I/O, and must return a dictionary, handle empty upstream outputs, and route evidence correctly. These constraints keep synthe-sized tools within the same primitive capability set as Static-SAGE while changing the granularity at which those capa-bilities are exposed. Verification Agent. Each implemen-tation is checked by a local verifier combining static checks with a stubbed dry-run that exercises the candidate without invoking the real tools; it enforces the evidence-return con-tract , rejecting tools that take a question-type argument or invoke reasoning in answer (verdict-committing) mode. On failure, the error is returned to the Implementation Agent for up to three retries; candidates that still fail are rejected. Af-ter validation, Dynamic-SAGE removes pure wrappers and duplicate compositions, and registers the accepted tools be-fore evaluation. Prompt-assembly and the full check list are given in Appendix S1. 

3.5. Inference with the Expanded Action Space 

At inference time, Dynamic-SAGE uses the same reason-ing loop as Static-SAGE . Given an evaluation sample 

(Vi, q i, Ci), the orchestrator either emits a final answer or selects a tool to obtain additional evidence. The only differ-ence is the action space: Static-SAGE selects from Ts, while Dynamic-SAGE selects from the expanded library Ts ∪ T d.When Dynamic-SAGE selects a primitive tool t ∈ T s,execution is identical to Static-SAGE . When it selects a synthesized tool gk ∈ T d, the orchestrator issues a single tool call, while gk internally executes its primitive compo-sition ρ(gk) and returns its output in the same format as a primitive tool. This is the efficiency mechanism: a re-curring pattern such as transcription followed by reasoning takes multiple visible orchestration steps in the static setting but a single higher-level action in the dynamic setting. 

3.6. Cost-Aware Evaluation Metric 

Final-answer accuracy alone does not capture the goal of Dynamic-SAGE. A dynamically expanded tool library is useful only if correctness and inference effort are weighed together. We therefore evaluate Static-SAGE and Dynamic-SAGE using paired correctness and paired tool-use reduc-tion on the same question-video pair. For each sample i and method m ∈ { s, d }, where s

denotes Static-SAGE and d denotes Dynamic-SAGE, we define correctness ymi = I[J(ˆ ami , a i)] , where J(ˆ ami , a i)

is a Boolean semantic judge that returns True when the predicted response ˆami is semantically equivalent to the ground-truth answer ai, and False otherwise. In our 5experiments, J is implemented using a GPT-4o judge that compares predicted responses against ground-truth an-swers for semantic equivalence rather than exact string match. Since correctness is determined automatically us-ing an LLM judge, we evaluate the robustness of this proto-col by repeating the complete evaluation using judges from three different model families (Claude [1], Qwen [18], and DeepSeek [3]); all evaluators consistently rank Dynamic-SAGE above Static-SAGE by 5–8%, indicating that the re-ported improvements are not an artifact of using GPT-4o 

as the evaluator (Table S5, Appendix S6). We use visible tool calls as the primary formal efficiency variable because they are directly recoverable from the in-ference trace, independent of API latency and provider pric-ing, and central to the objective of composite-tool synthesis. For each sample i and method m ∈ { s, d }, let nmi, tool denote the number of visible tool calls made by method m before producing its final response. We define the paired tool-call reduction as 

∆ei = nsi, tool − ndi, tool . (6) Thus, ∆ei > 0 indicates that Dynamic-SAGE uses fewer visible tool calls than Static-SAGE on sample i, ∆ei < 0

that it uses more, and ∆ei = 0 is tool-neutral. We report reasoning turns, latency, token usage, and monetary cost separately as descriptive efficiency measures. Each paired comparison is summarized by the tuple zi = ( ysi , y di , ∆ei),recording whether Dynamic-SAGE preserved, improved, or lost correctness and whether the outcome used fewer visible tool calls. We define six outcome groups by joint correctness 

(ysi , y di ) and the sign of ∆ei:

Gsafe : (1 , 1) , ∆ei>0; Gneutral : (1 , 1) , ∆ei=0; 

Goverhead : (1 , 1) , ∆ei<0; Gideal : (0 , 1) , ∆ei>0; 

Gcostly -gain : (0 , 1) , ∆ei≤0; Gloss : (1 , 0) .

(7) 

Gloss treats any correctness regression as a failure regard-less of tool-call count, since we consider accuracy loss un-acceptable irrespective of efficiency gains. Within Gloss , we report the distribution of ∆ei separately to distinguish cases where Dynamic-SAGE loses correctness while also increas-ing tool use from cases where it loses correctness while re-ducing it. Both-failure cases, where ysi = 0 and ydi = 0 , are re-ported separately and are not treated as positive outcomes even when Dynamic-SAGE uses fewer tool calls. 

## 4. Experimental Setup 

4.1. Benchmark and Protocol 

We instantiate the cost-aware paired protocol of Section 3.6 on the SAGE-Bench benchmark, comparing Static-SAGE against Dynamic-SAGE under a fixed orchestrator and primitive tool set so that the comparison isolates the ef-fect of the expanded action space. We evaluate on SAGE-Bench [7], a diverse VideoQA benchmark spanning seven duration buckets (0–60 s to 2400+ s), three modalities (vi-sual, verbal, both), four difficulty levels (easy, medium, hard, very hard), and two question formats (MCQ and open-ended). Following Algorithm 1 (Appendix S1), we stratify-sample H=150 questions as the synthesis holdout Dh,which is excluded from evaluation. SAGE-Bench contains 

1,744 questions ; after setting aside the 150-question syn-thesis holdout and removing 290 samples (about 17% of the remainder) whose source videos were unavailable when we collected the data, the evaluation split contains 1,304 sam-ples (595 MCQ, 709 open-ended). Because the videos are hosted externally, this exact split may be hard to reproduce later. We report in Appendix S8 how the dropped and re-tained samples compare in duration, difficulty, and modality so that the attrition is not silently selective; we also report the distribution of the held-out set. We report overall accu-racy, per-type accuracy (MCQ/open-ended), per-modality accuracy (visual/verbal/both), average visible and primitive tool calls per sample ( ni, tool ), average reasoning turns, wall-clock latency per sample, and GPT-4o tool cost per sample.

## 5. Results 

5.1. Headline Accuracy

67 .94% . We first establish this headline result and its statis-tical reliability across subgroups; the following subsections then decompose how the gain is achieved and at what cost. Table 3 reports subgroup accuracy together with paired statistical tests. Since Static-SAGE and Dynamic-SAGE are evaluated on the same question–video pairs, we test sig-nificance with McNemar’s test on the Dynamic-only and Static-only correct counts, and compute confidence inter-vals by bootstrap resampling over paired samples. 5.2. Efficiency Decomposition 

Having established the accuracy gain, we turn to its cost. Table 4 reports per-question resource usage for Static-SAGE and Dynamic-SAGE. The tool-call row corresponds directly to the paired efficiency variable from Section 3.6. Since ∆ei is defined as the number of visible tool calls saved by Dynamic-SAGE on sample i, the aggregate sav-ing is obtained by averaging ∆ei over the evaluation set. Dynamic-SAGE obtains a positive mean saving, ∆e =0.88 , indicating that the dynamically expanded tool library reduces visible tool use by nearly one call per question on average. Reductions appear consistently in reasoning turns, visi-ble tool calls, and latency, while token usage and cost in-crease. The visible-call saving, however, does not by itself show what happens to total effort: a composite tool counts as one visible call but executes several primitive operations internally. 5.4. Where Dynamic Tools Help and Hurt 

Breaking the paired outcome groups down by question cat-egory (Table S4 in Appendix S5) localizes these effects. By modality, loss is lowest on visual questions (6.3%) and highest on mixed-modality ones (8.5%), with verbal in be-tween (7.9%, N =76 ), so Dynamic-SAGE is most reliable on visual and least on combined evidence. By format, open-ended questions show both higher ideal (12.7% vs. 7.9%) and higher loss rates (8.3% vs. 5.2%) than MCQ, giving the expanded action space more room to both help and hurt when answers are unconstrained by choices. Long videos also show larger mean savings than short ones ( ∆e = 1 .24 

vs. 0.56 ), where the static agent would otherwise need longer trajectories. Loss rates stay non-negligible across all categories, so while every category improves on net (Sec-tion 5.1), the expansion adds per-category reliability risk rather than a uniformly safe improvement. 

5.5. Compression Failures and Tool Adoption 

Among the 90 Gloss samples, most losses (53%) occur when Dynamic-SAGE uses more tool calls than Static-SAGE, so the dominant failure mode is not premature over-compression but extended trajectories that still reach the wrong answer. Consistent with this, 51.1% of losses fall on hard-to-very-hard questions and 65.6% are open-ended, lo-cating the bottleneck where the expanded action space does the most work rather than in any single tool. Adoption is also non-uniform: two depth-2 tools account for most invo-cations, while deeper tools are rarely used and less accurate when they are, so dynamic synthesis mainly helps on fre-quent, shallow patterns. Full loss-subset and per-tool statis-tics are in Appendices S3 and S4 (Tables S2 and S3). 

## 6. Conclusion 

Inspired by VADAR [13], we introduce Dynamic-SAGE, an offline dynamic tool synthesis extension of the SAGE long-video reasoning framework [7]. Dynamic-SAGE generates reusable composite tools from held-out SAGE-Bench ques-tions and adds them to the agent’s tool library before eval-uation. In addition, we formalize cost evaluation, allowing us to study the accuracy and cost jointly for dynamic com-posite tool synthesis in VideoQA. The protocol lets us answer the question the gap posed, whether enlarging the action space helps once inference ef-fort is accounted for, rather than assume it. Dynamic-SAGE improves overall accuracy by 7.52 points ( p < 0.001 ) on the 1,304-question SAGE-Bench evaluation split while re-ducing reasoning turns and visible tool calls by around 28%, but increasing token usage and monetary cost by 34% and 26%, respectively. The answer is therefore conditional: the expanded action space helps, but it shifts cost from orches-tration steps toward per-call token consumption rather than reducing every axis, a multi-axis profile a scalar accuracy comparison would miss. Our paired comparison and analysis of pure losses lo-calizes the failures to difficult, open-ended questions that demand more effort from the pipeline. This indicates that synthesized tools’ routing and reliability on these difficult questions remain the main bottlenecks. Future work should focus on improving the quality, distinctiveness, and routing of synthesized tools rather than expanding the action space alone. Further evaluation on other benchmarks and orchestra-tors, including fine-tuned RL-trained ones, is needed, and we expect that sampling queries from a more uniform do-main distribution will yield more compositional and novel tools. 8References

## S1. Implementation Details 

This section lists the decoding and budget settings refer-enced in the main paper. Both Static SAGE ( GPT-4o or-chestrator) and Dynamic-SAGE run the GPT-4o orches-trator at temperature 0.0 with an iterative reasoning bud-get of N = 10 steps. Offline tool synthesis processes the held-out synthesis set Dh in batches of 15 and uses agent-specific sampling temperatures: the Signature Agent uses temperature 0.7 to encourage diverse candidate tool inter-faces, while the Implementation Agent uses temperature 0.3

to produce more stable executable code. The verification stage is deterministic. 

Implementation Agent prompt assembly. The Imple-mentation Agent is given the existing tool sources, the pro-posed docstring, the proposed signature, and the sibling sig-natures from the same generation batch. Its output is re-stricted to imports and an implementation body; the genera-tor then assembles the complete function using the signature and docstring produced by the Signature Agent. 

Verification Agent checks. The verifier first performs static checks, including Python syntax validation, banned-import rejection, docstring validation, and broad exception-handler rejection. It then imports the candidate in a con-trolled test module and dry-runs the function using place-holder inputs. To avoid expensive or side-effecting calls during verification, the original SAGE tools are replaced with strict stubs that mimic their runtime signatures and re-turn shapes.
